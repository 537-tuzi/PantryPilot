# PantryPilot 竞品与最佳实践调研

> 调研日期：2026-11-21　　调研范围：食材库存管理 / AI 膳食规划赛道的竞品形态、领域最佳实践、AI 与后端工程实践
> 目的：为 Sprint 2（AI 能力）与后续迭代提供决策依据；对照本仓当前实现，标出**差距**与**本仓已做对的地方**。
> 说明：竞品来源多为厂商博客与 SEO 榜单，有付费位与自我推荐倾向；量化数据（DAU、留存、营收）多数未公开核实，仅作方向性参考。

---

## 一、赛道结论（先看这里）

1. **功能已趋同，五件套是标配**：录入 → 临期提醒 → 库存扣减 → 菜谱匹配 → 购物清单。差异化主要在**社交/情感层**（家庭共享、投喂）与**AI 交互形态**。
2. **PantryPilot 的核心信条（AI 只给建议、事实由确定性程序负责 + 用户确认后扣减）在业界属于"重"的一档**。绝大多数竞品直接让 AI 写库或自动扣减。这带来两个后果：
   - 优势：可审计、可测试、模型不可用时核心功能不受影响 —— 这是**企业/合规场景**的卖点，也是本项目的教学价值。
   - 代价：交互多一步，转化率可能低于竞品。**需要用数据证明这一步值得**（见 §五 建议 1）。
3. **真正的竞争对手不是同类小程序，而是生鲜平台的 AI 模块**。叮咚买菜靠订单数据天然掌握批次与保质期，独立小程序在数据源上先天劣势。本项目的 `ingredient_catalog` + `expiry_date` 人工录入路线，应避开"数据源竞争"，转而竞争**规则严谨性**（过敏/禁忌硬校验、单位与批次一致性、事务与幂等）。
4. **业界共识正在从"纯 LLM 生成"转向"检索 + 约束求解 + LLM 只做解释与替换"**。本项目若继续沿用"把库存塞进 prompt 让模型出菜谱"，会在食材数量/用量/时间上持续产生幻觉，直接违反本仓"AI 输出必须经业务校验"的底线。

**市场数据（用于判断立项价值）**

- 中国城市家庭食物浪费率约 **10%**；叶菜在冰箱中损耗率可达 **20%–30%**。
- CHNS 研究：冰箱使用与家庭食物浪费增加 **24.35%** 相关，囤积心理是主因。
- 后浪研究所 732 份问卷：仅 **30.3%** 认为冰箱空间完全够用；**40.9%** 依赖线上按需高频下单。
- 全链条损耗浪费率约 **18%–20%**，年损失约 **1.15 亿吨**；家庭端约 5.0%。
- 政策：《反食品浪费法》+《粮食节约和反食品浪费行动方案》设定 2027 年量化目标。

**国内竞品暴露的短板（本项目应规避的坑）**

- **录入摩擦是致命伤**：用户坚持记录普遍不超过一周。入口必须有"录入一次成本 ≈ 0"的路径。
- **缺冷链/商超保质期数据**，也缺**菜品结构化保质期库**（按品类给默认保质期天数）。
- **独立小程序的数据源天然弱于生鲜平台** —— 不要在数据源上正面竞争。

### 2.3 竞品对本项目的三条可执行启示

1. **录入路径要"多入口 + 单一确认"**：手动 / 语音 / 拍照 / 小票 / 自然语言 多路进，最终都收敛到同一张"待确认草稿"表单上 —— 这正好契合本仓的 `IngredientDraft` + `uncertainties` 契约（草稿显式标注不确定项，用户确认后入库）。
2. **菜谱排序按"库存覆盖率"而非"评分"**：冰箱管家与 CookCLI 都用贪心集合覆盖（greedy set cover）给候选菜谱排序 —— 这是一个**确定性算法**，应该由程序做，LLM 只在覆盖率不足时给替换建议。
3. **家庭共享是刚需但本项目本期不做**：需求文档把"家庭多人共享与复杂权限"列入本期不做。竞品普遍把它当核心卖点。**建议明确记录为下一阶段候选**，而不是长期搁置。

## 三、领域最佳实践：食材库存管理

### 3.1 批次（Lot）级接收 —— 一切的地基

成熟做法是在**收货那一刻**同时记录批次号与到期/食用期，而不是等到卖出时。本项目已有等价设计：`inventory_items` 一行 = 一个批次（含 `quantity` + `expiry_date` + `purchase_date` + `storage_location`），流水表 `inventory_transactions` 是 append-only 变动账。

> **对齐检查**：本项目的 `inventory_items` 是"库存行"，批次语义由"行"承担（没有独立的 lot 号字段）。若未来要支持"同一次采购、同一天到期、同价"的多个批次合并显示，需补 `lot` 概念。这是**已知的模型简化**，不是缺陷，但要在文档里写清楚。

### 3.2 FEFO（先到期先出）

业界最常被引用的差异化能力：**让系统而不是人来决定先用哪一批**，库存自动轮转，浪费自然下降。

**本项目的差距**：计划确认扣减时，按 `inventory_item_id` 显式指定了要扣哪一批（ADR-0002），**不是自动 FEFO**。

这在本项目语境下**是一个需要显式决策的取舍**：

- 支持 FEFO：新增"按 `expiry_date ASC` 自动选批次"的扣减模式，符合行业最佳实践，也更省心。
- 坚持显式指定：批次可能被多个菜品共用（ADR-0002 的立题前提），自动选批次会让用户失去控制，且**必须由用户确认**才符合本仓信条。

**建议**：保留显式指定为默认（与 ADR-0002 一致），但在 `POST /inventory` 与计划确认的响应里**返回"该用户临期批次排序"**，让前端能提示"更临期的那批也可以用"。这样以极低成本获得 FEFO 的收益，不破坏既有契约。

### 3.3 临期提醒阈值分层

企业级做法是多档阈值（30/14/7 天）分级告警；面向家庭的应用通常更简单。

**本项目用单一 3 天窗口**（`EXPIRING_WINDOW_DAYS = 3`，ADR-0001），且**状态在读取时计算不落库**（避免状态字段过期 —— 这是好设计，业界同此判断）。

**差距**：3 天窗口偏窄，家庭采购周期通常以周计，大量"该尽快吃掉"的食材会落在窗口外。可考虑 `文档/03` 的首页/临期页改为**分档展示**（已过期 / 3 天内 / 7 天内 / 正常），但**底层判定规则保持单一窗口不变**（避免 §八 提到的常量漂移问题被放大）。

### 3.4 补货点与购物清单

企业做法：补货点 = 售罄率 × 在途量 → 自动转采购单。

**本项目**：购物清单是纯手工 + 可从计划导入缺失项（`POST /shopping-items/import-from-meal-plan`），**不自动下单**（这与需求一致，且是安全的默认值）。

**可借鉴**：补货点 = `default_servings` × 单份用量 − 当前库存，属于纯计算，程序可做，不必上 AI。

### 3.5 盘点与损耗归因

成熟系统把"数量变化"记成**有原因的事件**（报废/赠送/误操作），而不是静默调整。

**本项目已对齐**：`inventory_transactions.reason` ∈ add/adjust/consume/meal_plan_deduction，`delta_quantity` 带符号，metadata-only 变更写 `delta_quantity = 0` 的审计行。**这是本项目做得比多数竞品好的地方**（竞品多数只有"当前数量"）。软件化盘点/ shrinkage 报告可以后续做，但流水底座已具备。

### 3.6 单位处理 —— 本项目最明确的最佳实践缺口

调研到一个高度相关的失败模式：**"静默单位错配"**（silent unit mismatch）—— 发票用磅、菜谱用克、收银用"个"，三者对不上账，数字悄悄错掉且无人察觉。

业界共识做法：

- **每个维度一个规范基准单位**：重量→克，体积→毫升，计数→个。**在入口处转换一次**，下游不再做换算。
- **保留原始录入值** alongside 规范值，用于审计与将来补充密度数据后重新规范化。
- **质量与体积是不同维度**：没有该食材的密度数据时，**绝不把克换成毫升**。NIST SP 811 给出 oz/gal 等换算因子，但"杯→克"必须靠密度（USDA FoodData Central）；烹饪场景下"1 杯"的口径本身就有歧义（美制 236.588 mL vs 公制 250 mL）。
- 中国场景还存在"斤/两/克"的法定计量换算。

**本项目现状**：ADR-0002 §5 明确 **MVP 不做单位换算**，请求单位必须**同时等于**用料单位与库存单位，否则 400。

**评价**：这是一个**明确、有文档、有一致校验**的取舍 —— 符合"绝不做静默换算"的原则，比很多默默换算错掉的产品强。但它有两个代价：

1. 扣减路径上单位要检查**两次**（用料单位 + 库存单位），任何一处不一致都 400 —— 用户会频繁撞墙。
2. `inventory_items.unit` 是自由文本（`Text`），**没有受控词表**。`'g'` / `'克'` / `'G'` / `'克 '` 会被当成不同单位。

**建议（按投入产出排序）**

| 优先级 | 建议 | 理由 |
|---|---|---|
| P0 | 引入**受控单位词表**（质量/体积/计数三类，每类一个规范单位 + 中文别名表），入库时归一 | 不改契约就能消灭"同一个单位写成两种"的问题；比做换算便宜得多 |
| P0 | 拆分 `unit` 为 `unit` + `unit_kind`（mass/volume/count） | 让"能不能比"变成可判定的事，为后续换算留位 |
| P1 | 在 `ingredient_catalog.default_unit` 之上加**按品类的默认保质期天数** | 竞品"食鲜小笺"的做法；AI 录入时可直接给出到期日建议，减少用户输入 |
| P2 | 建立换算表（仅质量↔质量、体积↔体积），**保留原值** | 换算只在入口做一次；密度数据缺失时明确拒绝而不是猜 |

## 四、AI 架构最佳实践

### 4.1 业界共识的流水线

多份 2026 年的资料指向同一形状：

```
结构化库存（事实源）
  → 对真实菜谱语料的检索（向量/关键词/图混合）
  → LLM 作为规划器/编排器，受检索到的菜谱约束
  → 确定性校验层
  → 人工确认
```

**关键论断：LLM 不应是菜谱、用量、时间、营养的来源，只应是替换建议与解释的生成者。**

一个公开的对比很有说服力：某项目从纯 LLM 切换到 RAG 后，明确记录了纯生成方案的失败模式 —— 烹饪时间不准、用量泛化、营养数据缺失、**幻觉出不存在的食材与技法**；RAG 则给出可验证的菜谱与来源链接。

另一个国内工程指南给出了知识分层决策表，与本项目高度相关：

| 知识类型 | 手段 | 理由 |
|---|---|---|
| 频繁变化的事实（营养数据、时令、保质期库） | **RAG** | 成本最低，一���可上线 |
| 稳定的风格/输出模板 | LoRA | 微调 |
| 硬约束（菜单 schema、禁忌枚举） | **结构化输出 + 校验层** | **从第一天就要有** |

并给出推荐顺序：**先 RAG，再 LoRA，校验层第一天就上**；配合"生成 → 校验 → 重新生成"的闭环。

**对本项目的意义**：本仓 `app/ai/contracts.py` 已经定义好输出契约，`文档/06` 已定义"Context Builder 只传当前用户必要库存和偏好"—— **这正是 RAG 形态的第一层（检索范围限定为当前用户库存）**。Sprint 2 的关键设计决策是：

- **菜谱从哪来？** 当前 `recipes` 表是空的（只能由 seed 或直接写库产生），且**没有 `/recipes` 端点**。若让 LLM 自由生成菜谱，就落入"纯生成"路径，幻觉风险直接落到"用料数量"上。
- **建议**：Sprint 2 先做**基于 `recipes` 表的确定性检索**（按库存覆盖率排序，贪心集合覆盖），LLM 只负责在覆盖率不足时给替换建议与"用这些食材能做什么"的自然语言说明。这样：
  - 菜谱、用量、时间来自数据库（**符合本仓信条：事实来自确定性程序**）
  - LLM 输出仍然是草稿，经 Schema + 业务校验 + 用户确认
  - 评测指标（`文档/06` §7 的"库存匹配率""约束满足率"）变得可计算、可回归

### 4.2 人机确认（HITL）的设计要点

针对"AI 写操作必须人工确认"的设计，业界给出的可落地要点：

| 要点 | 说明 | 本项目现状 |
|---|---|---|
| 确认文案本身是接口的一部分 | 用户看不懂要执行什么，就会无脑点确认或一律拒绝 | ❌ 未实现（前端全空） |
| 分级：L0 读 / L1 可逆内部写 / L2 外部写 / L3 高危 | 按风险决定默认策略 | ✅ 本项目实际就是"L1 草稿 + L3 扣减"两级，**分级清晰** |
| **先确认再执行，不是执行后确认** | | ✅ 符合（预览 → 确认 → 事务） |
| 展示：影响哪个对象、关键参数、可否撤销、预期成本 | | ❌ 未实现 |
| 审计：请求人、模型/工作流版本、时间戳、参数摘要、结果 | ✅ 已有 `meal_plan_confirmations`（`request_hash` + `result_snapshot` + `operation_id`） | ✅ **这是本项目明显强于竞品的地方** |
| **超时不得默认批准** | 超时=拒绝，不是=通过 | ❌ 未实现（需在 AI 层落地时设计） |
| **必须测试拒绝路径** | "无法失败关闭的循环不算 HITL" | ✅ 本仓已有大量否定用例（单位不匹配、库存不足、禁忌、空 `ai_provider`） |
| 参数被编辑后要重新渲染最终动作 | 避免"确认的是 A，执行的是 B" | ❌ 未实现 |
| 幂等键 ≠ 鉴权 | 重放也要过权限检查 | ✅ 幂等作用域是 `UNIQUE(user_id, idempotency_key)` |

**本仓已有的两个"正确姿势"，值得在 AI 层照抄**：

1. `source_type` 由服务端从 `meal_plans.ai_provider` 推导，**客户端不得传入**（ADR-0002 §3）—— 这正是"不可信输入不能作为权限/事实依据"的落地。
2. 空 `ai_provider` 在**任何锁、任何流水写入之前**就 400 拒绝，且测试断言"零流水、零确认行、quantity 未变、version 未变"（`tests/api/test_meal_plan_confirm.py:688-712`）。

### 4.3 结构化输出的可靠性

针对 OpenAI 兼容接口的通用实践：

- **结构化输出是一个谱系，不是有无**。严格 JSON Schema 强约束（OpenAI/Anthropic/Google 支持）→ JSON mode（只保证可解析，不保证字段/类型/枚举）→ **prompt 内嵌 schema 契约**（DeepSeek/Mistral/部分自建网关只到这个层级）。
- **推荐的重试阶梯**：≤2 次带错误反馈的重试（把校验错误回传给模型让它自我纠正）→ 1 次换更强模型 → 然后**熔断**。总代价约 3× 延迟、4× 成本，把结构化失败率压到 ~0.05%。
- **每个 adapter 独立退避**，不要全局退避（不同厂商的限流头与重试语义不同）；记录 per-provider 延迟/错误率。
- **解析前先落原始响应**，解析失败可回溯；schema 版本变化时使缓存失效。
- **provider 层不许直接用 `requests`/`httpx` 调模型** —— 与本仓 `开发规范.md:213` 一致。

**给 Sprint 2 的具体建议**：

1. `app/ai/provider.py` 必须支持**三档降级**：严格 schema → JSON mode → prompt 内嵌 schema。当前 `.env.example` 的 `LLM_BASE_URL` 指向 OpenAI 兼容端点，不同厂商对 `response_format` 的支持差异很大 —— **不能假设所有兼容端点都支持严格 schema**。
2. `LLM_API_KEY` 应照 `SECRET_KEY` 的做法加一个校验器（当前 `config.py` 对 `llm_api_key` 没有校验，默认空串）。**空 key 时应让 AI 端点返回"AI 功能暂不可用"，而不是发起一个注定失败的请求。**
3. 落实 `文档/06` 的组件划分：`prompts/`（带版本号、纳入 Git）、Context Builder（限制条数与长度）、Output Parser（Schema）、Business Validator（过敏/禁忌/数量/单位/库存/状态）、Evaluation Harness（回归 AI-001~AI-008）。
4. **重试必须带错误反馈**，不能盲重试；熔断后 AI 端点应降级为 502/504（`AIProviderError`/`AITimeoutError` 已定义好），**且库存、临期、计划确认等非 AI 路径必须完全不受影响**。

### 4.4 上下文构建：只传必要信息

业界对"最小化上下文"的强调与本仓完全一致：

- 用户文本、库存数据、系统指令**必须分隔**，用户输入**始终视为不可信数据**（`文档/06` §5）。
- **不传密码/令牌**，限制输入长度、输出 token、调用频率。
- 只传当前用户的必要库存与偏好，**限制条数与长度**（Context Builder 的定义）。

一个值得单独提的失败模式：客服场景的"**库存谎言**"—— 模型宣称"已为你核对库存"，但实际未经程序校验。本项目的对策已经存在且正确：**模型只给建议，事实校验由确定性程序完成**。实现 AI 层时，要保证"让我核实一下库存"这类请求也走确定性查询路径，而不是让模型自己判断。

### 4.5 评测

`文档/06` §7 的指标定义已经是这个领域里相当完整的：

| 指标 | 本项目定义 | 落地建议 |
|---|---|---|
| 结构合格率 | 通过 Schema 的响应数 / 有效响应总数 | 用 `app/ai/contracts.py` 的 Pydantic 模型直接算 |
| 字段抽取准确率 | 逐字段人工标注比对 | **需要一份带标注的评测集**（`AI-001`~`AI-008` 只有 8 条场景描述，样本量偏小） |
| 库存匹配率 | 库存可满足的用料项 / 全部用料项 | **如果菜谱来自数据库而非 LLM，这个指标变成确定性的**，回归成本大降 |
| 约束满足率 | 人数/时间/预算/禁忌逐项判定 | 禁忌冲突为严重失败 |
| 延迟 | P50/P95，标注模型、网络、环境 | 需在 Provider 层埋点 |
| 恢复率 | 有限重试后恢复成功数 / 首次失败数 | 对应 §4.3 的重试阶梯 |

**建议**：在实现 AI 之前，先把**评测集扩到可回归的规模**（把 AI-001~AI-008 展开成每条 5~10 个样本），并把"结构合格率"和"库存匹配率"做成 CI 里的 Mock 用例（`tests/ai/` 目前是空目录，`pyproject.toml` 已注册 `ai` marker）。

## 五、后端工程最佳实践对照

### 5.1 分层

业界对 FastAPI 分层的共识与本仓声明一致：**Router → Service → Repository → ORM，单向依赖**；Router 保持薄（每处理函数 ≤10 行）；Service 拥有事务边界、返回 DTO 而非 ORM 模型；Domain 层零 FastAPI/SQLAlchemy 依赖；错误处理分层（避免吞异常，也避免泄露内部细节）。

**本仓对照**：

| 最佳实践 | 本仓现状 | 评价 |
|---|---|---|
| Router 薄 | ✅ 全部路由都是纯委派 | **符合** |
| Service 拥有事务边界 | ✅ `commit()` 只在 services | **符合** |
| Repository 只做数据访问 | ⚠️ `InventoryRepository.status_conditions()` 在 SQL 层重实现了一遍过期规则 | 规则双写，改常量会漂移 |
| Domain 层纯净 | ❌ `app/domain/` 空；领域规则以自由函数散在 services | **声明与实现不符** |
| 异常不吞、不泄露 | ✅ 统一 `AppError` → `{code,message,request_id}`；500 只回通用文案 | **符合，且优于多数实现** |

### 5.2 幂等

业界标准做法（Postgres 唯一约束 + 三态记录 + 原子 claim）：

```
INSERT INTO idempotency_keys (key, status) VALUES ($1,'processing') ON CONFLICT (key) DO NOTHING
-- rowcount==1 抢到；rowcount==0 已有记录
```

- 唯一约束作用域应为 `(user_id, operation, idem_key)`，避免不同用户撞键。✅ 本仓 `UNIQUE(user_id, idempotency_key)` 正是这个模式。
- `request_hash` 把键绑定到请求内容：同键不同内容 → 409。✅ 本仓已实现。
- 业务写入与幂等记录**必须在同一事务内提交**，否则崩溃会留下永久 `processing`。✅ 本仓是单事务。
- 业务上"故意失败"的响应**也应存储并重放**；只有能证明无副作用时才释放键。
- 需要 TTL 清理，且**键不得由服务端静默生成**（必须由客户端跨重试保持稳定）。

**本仓实现比标准做法更简洁也更稳的地方**：幂等检查**排在状态检查之前**，所以成功后的重试拿到首次结果而不是 409 —— 这是很多实现会踩的坑。唯一约束作为最终仲裁（`IntegrityError` → rollback → 重读 → 重放）也是标准做法。

**可借鉴的增强**：业界建议把幂等记录做成**通用表**（`api_idempotency`，含 `response_body jsonb`）而非只为 meal-plan 定制。本仓目前只有 `meal_plan_confirmations` 一张专用表 —— 若后续 AI 录入也需要幂等，可考虑抽通用层。

### 5.3 并发库存扣减

业界共识是**原子条件更新**而非"读-改-写"：

```sql
UPDATE stock SET qty = qty - :n WHERE id = :id AND qty >= :n
```

配合 `SELECT ... FOR UPDATE` 行锁处理跨行事务。

**本仓对照**：

- 计划确认：✅ `SELECT ... FOR UPDATE` 锁计划行 + 锁批次行（**按 id 升序加锁防死锁**）+ 校验 `row.quantity < total` → 409 `INSUFFICIENT_STOCK`。
- 库存修改：✅ 条件 UPDATE + `rowcount == 0` → 409。
- **可以补强的一点**：本仓是"先读出来在 Python 里比较，再 UPDATE"，不是单条原子条件更新。两者在行锁内等价，但**单条 `UPDATE ... WHERE quantity >= :n` 更难写错**，且天然幂等失败友好。

### 5.4 事务与重试

- 只对**安全操作**和**幂等调用**重试；固定间隔重试会在同一瞬间一起重试打爆下游 —— 必须**指数退避 + 随机抖动**，并设置端到端 deadline 预算。
- **批量操作要设上限**；不允许递归式"全部应用"。
