## 二、S1 缺陷

### S1-1 ✅ 已修复：备份失败留下 0 字节文件，恢复会清空数据库

**位置**：`scripts/dev.sh:149`（`cmd_backup`）、`scripts/dev.sh:153-164`（`cmd_restore`）、`scripts/restore.sh:26-31`

**实测复现**：

```
# (a) pg_dump 失败
$ docker compose exec -T db pg_dump -U pantry nosuchdb > /tmp/bt.sql
pg_dump: error: ... database "nosuchdb" does not exist
$ ls -la /tmp/bt.sql     → 0 bytes      ← shell 重定向先建文件，pg_dump 后失败

# (b) 用这个 0 字节文件跑恢复
DROP SCHEMA public CASCADE; CREATE SCHEMA public;   ← 表 t 消失
psql -v ON_ERROR_STOP=1 ... < /tmp/bt.sql           ← 空文件，退出码 0
→ 脚本打印「[OK] 恢复完成」
```

**为什么没被拦住**：

- shell 的 `>` 重定向**先创建文件**，命令失败也留下 0 字节文件；
- `pg_dump` 失败时 `set -e` 会让脚本退出，所以**不会打印「备份完成」**——但 0 字节文件已经躺在 `backups/` 里了；
- `cmd_restore` 对文件**不做任何校验**就 `DROP SCHEMA public CASCADE`；
- 空文件喂给 `psql` 是**合法操作**，退出码 0；
- 恢复后建议的验证命令 `curl http://localhost/health` **根本不查数据库**（`app/main.py:62-65` 返回静态字典），所以**清空后的库照样报「ok」**。

**已修**：

- `cmd_backup` 改为先写 `.partial` 临时文件，`pg_dump` 失败即删除并 `die`；空文件同样拒绝；
- `cmd_restore` 在清库**之前**校验：文件非空 + 含 `CREATE TABLE`，否则拒绝执行；
- `scripts/restore.sh` 同样加校验；
- 恢复后的提示改为指向 `/api/v1/health` 与一次真实查询，并注明 `/health` 不查库。

**修复后实测**：`POSTGRES_DB=nosuchdb bash scripts/dev.sh backup` → 退出码 1、`backups/` 文件数不变、无 `.partial` 残留；`restore /tmp/empty.sql` 与 `restore /tmp/junk.sql` 均拒绝执行、退出码 1；开发库 `inventory=6 users=3` 未受影响。

### S1-2 ✅ 已实测确认（未修，需团队决策）：应用连接的是数据库超级用户

**位置**：`deploy/docker-compose.yml:33`

```yaml
DATABASE_URL: postgresql+psycopg://${POSTGRES_USER:-pantry}:${POSTGRES_PASSWORD:-pantry}@db:5432/${POSTGRES_DB:-pantrypilot}
```

**实测**：

```
current_user = pantry
is_superuser = True
```

**后果**：ADR-0002 明写「应用账号对 `inventory_transactions` 仅有 SELECT / INSERT」，`docs/test-database-setup.md` 也把「流水表不可 UPDATE/DELETE/TRUNCATE」当作最小权限设计。**但仓库里根本没有应用账号的授权脚本** —— `deploy/docker-compose.yml` 让应用直接用 `postgres` 镜像初始化的超级用户。

也就是说：**追加式审计目前只靠应用代码自律，没有任何数据库层强制**。任何 SQL 注入、任何一处误写的 ORM 更新都能改写甚至删除审计流水。这与本项目对竞品的核心优势（可审计的事实数据）直接冲突。

**建议**（属于部署层改动，归 C 组）：

1. 加一个 `scripts/provision-app-role.sql`：建 `pantrypilot_app`（NOSUPERUSER），只授业务表的 SELECT/INSERT/UPDATE/DELETE，**流水表只给 SELECT/INSERT**；
2. `DATABASE_URL` 改用 `pantrypilot_app`；
3. 迁移必须由 `pantrypilot_owner` 拥有（`provision-test-maintenance-role.sql` 里已经假定这个角色存在了，但没人创建它）。

### S1-3 ✅ 已修复：`dev.sh check` 永远退出 2，自检根本不会跑

**位置**：`scripts/dev.sh:166-168`

```bash
cmd_check() {
  bash "$ROOT_DIR/scripts/check_env.sh" "${@:-}"   # ← 无参数时传入一个空字符串
}
```

**实测**：

```
$ bash scripts/dev.sh check
未知参数：（用 --help 查看用法）
exit=2
```

`check_env.sh` 的参数循环把空字符串落进 `*)` 分支 → 打印「未知参数」→ 退出 2。

**为什么重要**：`CLAUDE.md`、`团队上手步骤.txt`、`README.md` 都让成员用 `bash scripts/dev.sh check` 做自检。**这个入口从来没成功运行过**。`bash scripts/dev.sh check --fast` 能用（因为 `--fast` 是合法参数），所以这个 bug 很容易蒙混过关。

**已修**：改为 `"$@"`（bash 4.4+ 在 `set -u` 下展开为空是安全的，实测 `argc=0`）。修复后 `dev.sh check` → `PASS 17 / WARN 6 / FAIL 0`、退出码 0。

### S1-4 ✅ 已实测复现（未修）：登录接口的用户枚举时序侧信道

**位置**：`backend/app/services/auth_service.py:46`

**实测**：未知邮箱返回 **~0ms**，已注册邮箱返回 **~76ms**（Argon2id 验证的耗时）。响应体与状态码完全一致，纯 HTTP 客户端无法区分，**只能靠计时**。

**后果**：攻击者对每个候选邮箱发 10 次取中位数，1 万个候选约 13 分钟即可枚举出全部已注册账户，再配合下面 S2-3 的注册接口显式 409 oracle，攻击面更大。

**建议**：用户不存在时也执行一次等价的 Argon2id 验证（对着固定 dummy hash），使两条路径耗时对齐；或统一对两种失败返回同样的最小延迟。

### S1-5 ⚠️ 待核实：开发数据库以默认弱口令发布到宿主机端口

**位置**：`deploy/docker-compose.yml:22`（`"${DB_PORT:-5432}:5432"` 绑定 `0.0.0.0`）、`:9`（`POSTGRES_PASSWORD` 默认 `pantry`）

**已实测确认的部分**：端口确实绑定在 `0.0.0.0`（`docker compose ps` 显示 `0.0.0.0:5432->5432/tcp`），默认口令确实是 `pantry`。

**还需核实的部分**：`.env.example` 让成员改 `POSTGRES_PASSWORD`，但 **postgres 镜像只在数据卷首次初始化时应用该变量** —— 已有数据卷时改 `.env` 不生效。这与 `pantrypilot` 容器里的应用账号密码是否被 compose 插值同步，是两条不同的链路。

**实测到的关键事实**：

- **compose 的变量插值不读根目录 `.env`**。compose 的项目目录是 compose 文件所在的 `deploy/`，它找的是 `deploy/.env`（不存在）→ 全部回落到默认值。
- **但 `dev.sh` 会 `set -a; . ./.env; set +a` 把根 `.env` 导出到 shell 环境**，而 **shell 环境变量在 compose 插值中优先级最高** → 所以 `dev.sh` 路径下根 `.env` **是**生效的，直连 `docker compose` 则**不是**。
- 实测：`FRONTEND_PORT=8099 docker compose config` → `published: "8099"`；不加 → `80`。而本机根 `.env` **根本没有** `FRONTEND_PORT` 等变量（只定义了 14 个，`POSTGRES_*` 与 `*_PORT` 全缺），所以目前是靠默认值"碰巧对上"。

**后果**：`README.md` 的「底层等价命令」直接写 `docker compose -f deploy/docker-compose.yml up -d --build` —— 这条路径**不读**根 `.env`。成员改了 `.env` 的端口或口令，走这条路径就会不生效，且没有任何提示。

**建议**（C 组）：

1. `deploy/docker-compose.yml` 顶部加 `env_file` 之外的显式说明，或在 `dev.sh` 里统一用 `--env-file "$ROOT_DIR/.env"`；
2. `check_env.sh` 增加一项：比对根 `.env` 与 compose 实际解析出的端口/口令是否一致；
3. `bootstrap.sh` 在 `.env` 已存在但缺少 `POSTGRES_*`/`*_PORT` 时补齐（现在只在 `.env` **不存在**时才从 `.env.example` 复制）；
4. 生产部署（`文档/08`）不应把 5432 发布到公网。

### S1-6 ⚠️ 待核实：前端类型定义与后端契约不符（两个文件）

**位置**：`frontend/src/types/api.ts:7`（`InventoryItem`）、`:39`（`MealPlan`/`RecipeCandidate`）

扫描代理指出：

- `InventoryItem` **缺** `status` / `version` / `ingredient_id`，**多**了后端不返回的 `category`。影响：`PATCH /inventory/{id}` 的 `expected_version`（必填 `ge=1`）**无法组装**，会直接 400。
- `MealPlan` / `RecipeCandidate` 抄的是 **AI 内部契约**（`app/ai/contracts.py`），**不是 HTTP 契约**。而 `GET /api/v1/meal-plans/{id}` 返回的是 `items[]` 与 `request_constraints`，**没有** `recipes` / `missing_items` / `constraint_notes` / `warnings` —— UI-08 一接就是白屏。

**为什么标"待核实"**：这两条与我自己独立发现的「前端产物里根本没有 HTTP 层」相互印证，但**类型层面的具体字段差异我没有逐字段比对过**。

**建议**：A 组实现 UI-01 之前，先把 `src/types/api.ts` 改成**从后端 OpenAPI 生成**（`/openapi.json` 已经可用），而不是手抄。否则每个页面都会重蹈覆辙。

### S1-7 ⚠️ 待核实：`format.ts` 的「今天」锚点来自浏览器时区

**位置**：`frontend/src/utils/format.ts:21`

扫描代理的实测：Node 里 `TZ=America/New_York` 时 `new Date('2026-11-18').getDate()` 返回 **17** —— ISO 裸日期被当成 UTC 零点再按本地读回，导致**每天有 8 小时与服务端差一天**。

这与我独立发现的「前端重算 3 天阈值，而服务端也判定」是同一片区域的问题（ADR-0001 明确状态由服务端算）。**但 `expiryStatus()` 是否真的用 `new Date()` 锚定、还是由调用方传入 `today` 参数，我需要再看一眼**——`format.ts` 的 `expiryStatus(expiryDate, today, thresholdDays)` 签名上 `today` 是**入参**，所以影响范围取决于调用方。

**建议**：前端一律用服务端返回的日期做锚点（`/dashboard/summary` 已返回 `statistics_date`），不要用浏览器本地时间推算。

## 三、S2 缺陷（节选，按价值排序）

### S2-0 ✅ 已复现并已修：nginx 启动时解析上游，后端换 IP 后前端持续 502

**位置**：`deploy/nginx.conf:17`

**实测复现**（构造后端换 IP 的场景）：

```
后端从 172.18.0.5 换到 172.18.0.6（前端容器未重启，nginx 仍缓存 .5）

nginx 日志：
  [error] connect() failed (111: Connection refused) while connecting to upstream,
          upstream: "http://172.18.0.3:8000/api/v1/health"
前端：HTTP 502 Bad Gateway
后端直连 :8000/api/v1/health：HTTP 200     ← 后端本身完全正常
```

**触发条件是日常操作**：`dev.sh up`、`docker compose up -d --force-recreate`、机器重启。修复前只能手动
`docker compose restart frontend` 才能恢复 —— 而后端明明是好的，很容易误判成"后端挂了"。

**已修**：`nginx.conf` 加 `resolver 127.0.0.11 valid=10s ipv6=off;`，并把 `proxy_pass` 改成**变量形式**：

```nginx
set $backend http://backend:8000;
proxy_pass $backend$request_uri;
```

变量形式的 `proxy_pass` 才会让 nginx 在**每次请求时**用 `resolver` 重新解析主机名。
⚠️ 注意：变量形式的 `proxy_pass` **不会自动带上原始 URI**，必须显式拼 `$request_uri`（否则 `/api/v1/auth/login`
会被截成 `/`）。`/health`、`/docs`、`/openapi.json` 三个 location 同样要改。

**修复后实测**：同样的换 IP 场景（后端 `.5`→`.6`，`.5` 被别的容器占用）→ **HTTP 200，无需手动重启前端**，
nginx 日志无 502。

## 四、S3 与「做得对、不要动」的地方

### 做得对、**明确不要改**的地方（51 条正面结论中的重点）

这些是本项目相对竞品的核心优势，改动时务必保留：

1. **幂等重放逐字节一致** —— `request_hash`（SHA-256 规范化 JSON，与请求字段顺序无关）+ `result_snapshot` 存业务结果。
2. **幂等检查刻意排在状态检查之前** —— 成功后的重试拿到首次结果而不是 409。这是很多实现会踩的坑。
3. **`source_type` 由服务端从 `ai_provider` 推导**，客户端不得传入（ADR-0002 §3）。
4. **空 `ai_provider` 在任何锁、任何流水写入之前就 400 拒绝**，且有测试断言"零流水、零确认行、quantity 未变、version 未变"。
5. **跨实体访问返回 404 而非 403**，不泄露存在性。
6. **`session.commit()` 只出现在 `app/services/`** —— 实测 `grep -rn "\.commit()" backend/app/ | grep -v app/services/` 零命中。
7. **每次数量变化都写一条流水**，`sum(delta_quantity) == quantity` 不变量有测试断言（**注意：`scripts/seed.py` 曾绕过它，已修**）。
8. **批次按 `sorted(totals, key=str)` 升序加锁** —— 防死锁约定。
9. **请求校验错误不回显请求体** —— `request_validation_error_handler` 刻意避免回显含密码的内容。
10. **日志脱敏已覆盖 `Authorization: Bearer`、`password|secret|token =`、`postgresql://user:pass@`**（但覆盖不全，见 S2）。
11. **`tests/conftest.py` 的库名守卫硬失败**（`RuntimeError` 而非 skip）—— 确保测试永远打不到开发库。
12. **接口错误结构统一** `{code, message, request_id}`，且响应头与响应体的 `request_id` 一致（有断言）。
