## 一、关键环境事实：Docker 权限报错多半不是 Docker 坏了

本机 `docker ps` 一开始报 `permission denied while trying to connect to the docker API`，但：

```bash
$ getent group docker
docker:x:999:psh          # ← 用户其实已经在 docker 组里了
$ id -nG
psh adm cdrom sudo dip plugdev lpadmin lxd sambashare   # ← 但当前 shell 的组身份没刷新
```

`scripts/install_docker.sh` 把用户加进 `docker` 组，但**已经打开的登录 shell 不会自动获得新组**。

- 修复（当前 shell 生效）：`newgrp docker`
- 修复（一次性切换，适合脚本里）：`sg docker -c 'docker ...'`
- 彻底修复：注销后重新登录

> **团队影响**：任何装了 Docker 但没有 `newgrp docker` 或重新登录的成员，都会以为「Docker 装坏了」，从而走到 `bootstrap.sh` 的宿主机 venv 兜底分支（而 Ubuntu 22.04 的 Python 是 3.10，后端根本跑不起来），最后卡在「后端无法运行」。**这是最值得在上手文档里加一句的地方。**

## 三、本次发现并**已修复**的缺陷

### 缺陷 1（S1）：`dev.sh test-db` 先授权后迁移 → 新成员第一次跑测试就失败

**现象**（全新测试库上实测）：

```
==> 配置测试维护账号（顺序：先迁移库，再授权）
psql:/scripts/provision-test-maintenance-role.sql:48: ERROR:  relation "users" does not exist
[OK] 维护账号已配置          ← 明明失败了却报成功
==> 对测试库执行数据库迁移   ← 迁移发生在授权之后
...
FAILED tests/api/test_inventory.py::test_optimistic_lock_blocks_concurrent_database_updates
FAILED tests/api/test_meal_plan_confirm.py::test_row_lock_serializes_concurrent_confirmations
sqlalchemy.exc.ProgrammingError: (psycopg.errors.InsufficientPrivilege)
    permission denied for table meal_plan_ingredients
2 failed, 98 passed
```

**三层问题**：

1. **顺序错**：授权脚本按表级权限 `GRANT`，业务表必须先存在（`docs/test-database-setup.md` 早已写明），但代码把授权放在迁移前面。
2. **psql 没开 `ON_ERROR_STOP`**：SQL 报错后 psql 仍返回 0，脚本继续执行并打印 `[OK] 维护账号已配置` —— **静默撒谎**。
3. **文档自相矛盾**：`docs/test-database-setup.md:19` 写「建库 → 授权 → 迁移」，第 20–21 行却写「必须先有业务表存在」。

**后果**：新成员第一次执行 `bash scripts/dev.sh test` 就是红的，而且报错信息（权限不足）与真实原因（顺序错了）完全对不上号，排查成本极高。第二次执行才会变绿 —— 这类「第一次红、第二次绿」的问题最消耗信心。

**修复**（`scripts/dev.sh` + `docs/test-database-setup.md`）：

- 顺序改为 **建库 → 迁移 → 授权**；
- 授权步骤加 `-v ON_ERROR_STOP=1`，失败即以非零码退出；
- 提示语改为「配置测试维护账号（迁移之后授权）」，不再自相矛盾；
- 文档统一为正确顺序，并说明「未开 `ON_ERROR_STOP` 会继续执行并报成功」这一坑。

**修复后验证**：删掉测试库 → 单次 `dev.sh test` → **100 passed**；维护账号权限复查为 13 项（`users`/`inventory_items`/`recipes`/`meal_plans`/`meal_plan_items`/`meal_plan_ingredients` 各 SELECT+DELETE，`inventory_transactions` **仅 SELECT**），与设计完全一致。

### 缺陷 2（S2）：`seed.py` 重复执行会让演示库存成倍翻倍

`users` 和 `ingredient_catalog` 都用了 `ON CONFLICT`（幂等），但 `inventory_items` 的插入**没有任何冲突处理**。实测连跑两次后：

```
牛奶 x2  qty=2.000    牛肉 x2  qty=800.000    番茄 x2  qty=1000.000
菠菜 x2  qty=600.000  酸奶 x2  qty=4.000      鸡蛋 x2  qty=12.000
```

而 `团队上手步骤.txt` 是把 `seed` 当常规步骤写给新成员的。

**修复**：写入前先清理「演示账户 + 本脚本那组（名称, 单位）」的旧批次，再重新写入。范围严格限定，手工添加的条目不受影响。实测 12 → 6 → 6，稳定。

### 缺陷 3（S2）：`seed.py` 写入的库存**没有任何流水**

演示数据的 `inventory_transactions` 为 **0 行**，直接违反本仓的核心不变量 `sum(delta_quantity) == 当前 quantity`（`tests/api/test_inventory.py` 有断言，但只覆盖 API 路径）。

后果：项目最有特色的「追加式审计流水」在演示环境里是空的；演示账户之后再改数量，流水更是永远对不上账。

**修复**：每次入库同步写一条 `inventory_transactions`（`reason='add'`、`source_type='manual'`、`operation_id=NULL`）。实测 `MISMATCHED_ITEMS=0`。

### 缺陷 4（S2）：`seed.py` 的「今天」用的是系统日期，与应用的「今天」差一天

```python
today = date.today()      # 旧
```

容器系统时区是 **UTC**（实测 `date` → `2026-11-21 11:16 UTC`），而临期判定按 **Asia/Shanghai**（`2026-11-21 19:16`）。`docs/adr/0001-app-timezone.md` 明确规定统一用 `APP_TIMEZONE`。原实现意味着**每天有 8 小时（UTC 16:00–24:00，即上海时间次日 0 点起）演示数据的到期日会算错一天**。

**修复**：改用 `datetime.now(ZoneInfo(settings.app_timezone)).date()`，与应用、与 ADR-0001 同一来源。实测播种日与应用的「今天」一致。

### 缺陷 5（S3）：`docs/test-database-setup.md` 自相矛盾

见缺陷 1 第 3 点，已一并修正。

## 四、本次发现但**未修改**的问题（需团队决策）

### 4.1 前端产物里根本没有 HTTP 层 —— 登录流程在生产镜像中不可达

实测导入关系：

```
grep -rn "stores/auth" src/    → 无任何命中（stores/auth.ts 自己不 import 自己）
grep -rn "api/client"  src/    → 只有 src/stores/auth.ts 命中
grep -rn "AppLayout"   src/    → 无任何命中（孤儿组件）
```

再查构建产物：

```
grep -c baseURL          /usr/share/nginx/html/assets/index-*.js   → 0
grep -o "pantrypilot.token" ...                                      → 无
```

**即：整个 axios 实例、JWT 存取、登录流程都被 tree-shaking 从镜像里剔除了。** 用户打开 `http://localhost/` 没有任何办法登录 —— 因为 10 个页面全是占位符，没人 import auth store。

这不是「占位符还没写」的普通待办，而是**架构层面的断裂**：等 A 组实现第一个真实页面时，如果忘记 import store，整条数据层仍然不会进包，而且没有任何构建期错误提示。

**建议**：在实现 UI-01 登录页时，第一件事是接 `useAuthStore`；并在 `App.vue` 或 `main.ts` 里做一次「路由守卫 + store 初始化」，让 token 恢复成为应用启动的一部分。

### 4.2 `bootstrap.sh` 的 `SECRET_KEY` 写入是静默失败

```bash
python3 - <<'EOF' 2>/dev/null || true   # ← 失败也被吞掉
...
EOF
ok "已生成 .env 并写入随机 SECRET_KEY"   # ← 无论成败都报成功
```

若这段 Python 因任何原因失败（例如 `python3` 不存在、`.env` 里占位符字符串被改过），脚本仍会打印成功，而后端会以「SECRET_KEY 缺失或仍为默认占位符」拒绝启动 —— 排查成本高。建议改成写完后回读校验，再决定报成功还是 `die`。

### 4.3 迁移 `20261121_0002` 的约束名带重复前缀

```
ck_shopping_items_ck_shopping_items_quantity_positive
```

原因：迁移里写的是 `op.create_check_constraint("ck_shopping_items_quantity_positive", ...)`，**没有用 `op.f()`**，而 Alembic 会再套一层 `ck_%(table_name)s_%(constraint_name)s` 约定。同目录的迁移 `0001` 用的是 `op.f("ck_shopping_items_status_allowed_values")` —— 写法不统一。

**影响评估（已实测）**：

- 约束**功能正常** —— 实测插入 `quantity=0` 被正确拒绝；
- **autogenerate 不报漂移** —— 实测 `alembic revision --autogenerate` 生成的 `upgrade()` 是空的；
- `downgrade` 也能正常回退。

所以这是**外观问题**，不值得单独发一个迁移。**建议**：B 组下次动这块时，用新增迁移（不要改已合并的迁移）把名字改成 `ck_shopping_items_quantity_positive`，并统一用 `op.f()`。

### 4.4 开发库里残留了手工测试账号

开发库 `pantrypilot` 的 `users` 表里有三个账号：

```
testuser | test@example.com | 2026-11-21 06:50
vuser    | vuser@example.com | 2026-11-21 06:58
demo     | demo@example.com  | 2026-11-21 07:13
```

`testuser` / `vuser` 在**仓库里搜不到任何出处**（`grep -rn "testuser\|vuser"` 无命中），是有人手工写库/跑临时脚本留下的。它们会被 `dev.sh backup` 一并备份进备份文件。

**建议**：由数据库属主确认后清理；并考虑在演示库初始化时只保留 `demo` 账号。

### 4.5 `seed.py` 演示数据不覆盖 `recipes` 与膳食计划

`recipes` 表在演示库里是 **0 行**，`meal_plans` / `meal_plan_items` / `meal_plan_ingredients` 也没有任何创建路径（HTTP 没有，seed 也没有）。也就是说 **ADR-0002 设计的「计划确认 → 事务扣减」闭环，在演示环境里无法被走通**（只有测试夹具能造出这些数据）。

**建议**：把「灌一份可确认的演示膳食计划（含用料行、绑定到演示库存批次）」列入 Sprint 2 —— 这是 AI 能力落地前必须先补的地基，否则 AI 生成的计划无法被用户确认，核心闭环断在这里。
